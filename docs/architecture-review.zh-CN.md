# Design-X：独立架构评审（中文版）

**评审对象：**《Design-X——AI 原生视觉创作工作室：架构提案与独立评审简报》，资料截止日期为 2026-10-30。  
**评审日期：**2026-10-30。  
**同时评审：**当前 `design-x` 仓库：基于 React 19 和 Vite 的原型，使用本地规则模拟 AI（`../../src/lib/studioModel.js`）、自定义 Canvas2D/SVG 编辑器（`src/components/Editor.jsx`）及 localStorage 持久化。

> **阅读说明：**原文中 **[V]** 表示评审时查阅了公开来源；**[V2]** 表示仅依据博客、转售商或镜像等二手资料，需向供应商确认；**[U]** 表示工程判断或未经验证。第 11、12 节的阈值是**建议假设**，不是实测基准。原评审环境无法直接获取 `developers.openai.com` 和 `remotion.dev` 页面，相关信息来自搜索引擎收录的页面副本。本文件转述原评审意见，不代表已重新核验这些事实、价格或法规。

## 0. 总体结论

1. 提案中最重要的判断是正确的：**可编辑创作文档是产品的核心**；模型负责产生内容，确定性工作进程负责渲染，Agent 是可选能力。直接操作无需经过 Agent。
2. 需要重新审视的不是“一个 Codex harness 是否足够”，而是“沙箱化编码 Agent harness 是否适合作为创作 Agent 的基础”。创作 Agent 的操作都是对 Design-X 类型化 API 的调用，并不需要 shell、文件系统或微型虚拟机。建议在控制平面内运行供应商无关的工具调用循环，为常见场景增加确定性的 **Recipe（创作配方）**，把代码沙箱作为可选工具；只有基准测试证明代码执行有明显价值时，再考虑 Codex 或托管 Agents API。
3. 一个 Agent 循环通常足够。批量营销、长视频任务需要工作流；视觉质检需要评估模型调用；其他能力可由确定性服务完成。增加第二个自主 Agent 前必须先测量。
4. 上线区域尚未确定：中文产品和豆包/火山引擎、阿里云 OSS 与美国服务 Codex/E2B 之间存在区域、数据驻留和合规问题。先确定中国大陆还是全球市场，再确定模型、存储和合规方案；火山引擎与国际版 BytePlus 的端点及模型可用性也不同。
5. 最难的技术风险之一是**编辑器与服务端导出的一致性**：文字布局、中文字体、输入法和导出效果必须一致。建议使用与渲染器无关的文档模型，在浏览器用 DOM/SVG 渲染，服务端用无头 Chromium 执行相同渲染代码；先通过技术验证。
6. 模板与布局是 MVP 基础设施。既然要求可编辑文字和布局、不能依赖事后拆层，就必须从第一天提供受约束的模板和布局语法。美图的技能目录更像参数化创作配方。

保留文档、资产、任务、适配器与工作进程等领域架构；把模板、渲染一致性、审核与标识、额度管理纳入 MVP；多供应商网关、复杂视频时间线及多 Agent 留待后续。

## 2. 架构验证

### 2.1 可简化或推迟的部分

- **每会话 E2B 沙箱承载 Codex、专用 Sandbox Bridge 和线程映射：**创作操作主要是 HTTP 调用，额外引入冷启动、认证、恢复与成本。改为控制平面内 Agent 循环；确有代码执行需求时提供 `code.run` 沙箱工具。会话及调用日志保存到 Postgres。
- **独立创作能力网关及路由策略：**MVP 使用进程内适配器和能力注册表，每项能力接入一家供应商。
- **独立视频时间线引擎：**MVP 使用镜头列表组成的分镜文档，结合 FFmpeg 拼接、字幕导出。
- **通用 `approvals.request` 工具：**大部分审批属于费用门槛；由服务端预算策略在超额时暂停即可。

### 2.2 缺失的基础能力

| 能力 | 作用 | 阶段 |
|---|---|---|
| 模板与布局系统 | LLM 填充槽位，图片模型填充像素槽位，保证结果可编辑。 | MVP |
| 预览渲染器 | 文档转图片，供 Agent 检查排版、溢出、对比度，也用于缩略图和导出。 | MVP |
| 字体服务 | 中文字体体积较大，需要子集化和按需加载；检查商用嵌入许可，并保证前后端字体一致。 | MVP |
| 输入/输出审核 | 面向公众的生成产品需要安全审核。 | MVP |
| AI 内容标识与来源 | 中国及欧盟等市场涉及显式/隐式标识或透明度要求；适用范围由法律顾问确认 [U]。 | 对应地区 MVP |
| 计量、配额与积分 | 支付可后做，但需要先限制单用户与单轮消耗。 | MVP 配额 |
| 图片交付与变换 | 缩略图、响应式预览与格式转换，可用 imgproxy 或云服务处理。 | MVP |

| 结构化品牌套件 | 颜色、字体和 Logo 作为模板及 Agent 可引用的令牌。 | MVP 最小版 |

### 2.3 扩展性与可靠性

供应商限流通常比 CPU 更早成为瓶颈：按供应商和模型限制并发、按租户公平排队。拖动操作在松开指针或约 500 毫秒空闲后合并写入；使用操作日志和快照。横向扩展时，SSE 需要 Redis pub/sub 或 Postgres `LISTEN/NOTIFY`。大文件通过预签名 URL 直传/直取，供应商结果由工作进程转存。未引用的生成素材可按用户可见条款设置分层与过期策略，例如 30 天转低频、180 天删除。对非终态供应商任务运行定期对账。

## 3. Agent 设计

### 3.1 工作性质

提案中创作 Agent 的工具均为对 Design-X 状态的类型化操作，而不是编译代码、修改仓库或运行测试。只有需要生成特殊 SVG、图表、Python 图像变换或 Remotion 代码时，沙箱才可能有价值。

### 3.2 方案比较

| 方案 | 优势 | 不足与定位 |
|---|---|---|
| A：仅配方 | 确定性、低成本、可测试，适合技能目录。 | 模糊的多轮对话能力较弱；直接功能、批处理和高频场景仍需要它。 |
| B：自建工具调用循环 | 运行在控制平面，无额外基础设施，便于控制预算、审批、取消和续轮；可适配兼容接口 [U]。 | 需要自行管理上下文；**推荐默认方案**。 |
| C：OpenAI Agents SDK | 提供交接、护栏、追踪和 MCP [V2]。 | 受 SDK 抽象约束，需确认非 OpenAI 模型支持；可作为 B 的替代。 |
| D：E2B 内 Codex App Server + 桥接 | 编码能力强，支持上下文压缩与审批。 | 桥接、冷启动、会话上限、连接恢复及实验性动态工具增加复杂度 [V/V2]；仅在代码执行被证明重要时使用。 |
| E：托管 Agents API | 原评审称可减少桥接与 harness 运维 [V]。 | 处于 beta，区域、数据驻留、零数据保留与自定义工具能力需确认 [U/V2]。 |
| F：多 Agent | 可划分规划、设计和评估角色。 | 费用、延迟、冲突与调试复杂度增加；推迟。 |

建议采用 **A + B**，通过 `AgentRuntime.run_turn(session, input) -> stream[Event]` 隔离运行时，使 SDK 或托管方案可替换。

### 3.3 单循环的边界

商品主图与社媒图使用配方；直接拖动和改标题走操作 API，聊天中的简单修改可使用一次轻量模型调用。六个方案择优使用视觉模型、OCR 和商品相似度评估。200 SKU × 4 尺寸使用工作流扇出，仅异常交给 Agent。视频分镜到多个片段采用异步续轮。自评与修改设置最大轮数。只有某类任务的失败率差距达到原文假设的 30%，且替代方案在成本和延迟范围内持续改善，才考虑第二套 harness 或多 Agent。

### 3.4 若仍选 Codex

优先评估地区与数据限制允许的托管方案。自行部署时，沙箱内使用稳定的 stdio 运行 `codex app-server`，桥接仅向控制平面发起经认证的 WebSocket/gRPC 连接，不暴露入站端口；固定版本并使用短期会话令牌。创作工具由控制平面的 MCP 服务提供，并逐次检查项目权限。Postgres 保存权威对话及工具日志，Codex 线程仅作缓存。审批映射到应用审批表、经 SSE 展示并设置超时拒绝；取消时中断轮次并按策略取消任务。不要每条消息都启动一次 `codex exec`。

## 4. 推荐架构

### 4.1 架构 A：最简可行 MVP

面向约 3–5 名工程师：一个模块化 API、独立工作进程、Postgres、Redis 和对象存储。浏览器包含对话、Board、画板编辑器、资产及共享文档核心；API 包含身份/权限/配额、文档、资产、Agent、供应商适配器和任务接口。生成、渲染、图像处理工作进程领取数据库任务；浏览器通过预签名 URL 访问对象存储；事件通过 Redis 返回 API。

部署可使用同一镜像的 `api` 和 `worker` 入口；Chromium 与字体需要单独渲染镜像。使用托管 Postgres、Redis 和对象存储，设置预发布及生产环境。优点是开发调试简单；极大规模扇出或 Agent 代码执行不是该阶段重点。原文对 Postgres 队列吞吐的估计为每秒数百至数千任务 [U]。

### 4.2 架构 B：生产增长

仅在指标触发时增加工作流引擎、独立能力网关、Yjs 协作服务、GPU 资源池、可选代码沙箱、读副本与分区。触发条件分别包括：跨供应商工作流超过三步且有人工等待、每种能力超过两家供应商或多服务共享配额、出现实时多人编辑需求、自托管更经济或数据驻留要求、基准证明代码执行有价值，以及数据库长期资源压力或操作日志规模达到约 5 亿行 [U]。原评审估计增长架构需要约 10–15 名工程师。

## 5. 推荐的 Agent 运行时

### 5.1 工具接口

以 `recipes.run(recipe_id, params)` 和 `canvas.apply_ops` 替代独立创建文档工具，优先从模板开始。增加 `canvas.render_preview(doc_id, revision, artboard_id)` 供视觉检查；`canvas.describe(doc_id)` 返回图层 ID、语义角色、文本、边界与溢出状态。预算策略由服务端执行，长任务使用 `jobs.await` 让出当前轮。图层角色包括 `headline`、`product`、`background`、`logo`、`cta`、`badge`，使“放大商品”可映射到明确对象。

每次调用应经过 JSON Schema 验证、用户和项目授权、费用计量，并记录输入、输出、成本与延迟。

### 5.2 状态机与限制

状态为 `running → awaiting_approval / awaiting_jobs / completed / cancelled / failed`。审批通过后恢复，拒绝或超时结束；任务终态到达后开启系统续轮。原文提出每轮最多 25 次工具调用、120 秒活跃 LLM 时间及按套餐配置的成本上限，均为假设。取消在步骤之间检查；进行中的供应商请求视其能力完成或取消。

### 5.3 异步续轮

用户提出视频请求后，Agent 建立分镜、提交三个带幂等键的视频任务并结束当前轮。任务队列提交供应商、接收回调或轮询，转存并审核资产，所有任务终态后由 API 发起续轮，Agent 再编排片段和字幕并提交渲染。等待期间不保留进程状态；任何实例均可从 Postgres 对话记录恢复上下文。

### 5.4 上下文管理

保留最近若干消息、滚动摘要和最新文档描述；图片以受限分辨率的渲染预览引用传入，避免直接携带原始上传文件。

## 6. 多模态集成

### 6.1 适配器接口

先使用进程内适配器，统一图片生成/编辑/拆层、抠图、放大、视频生成、视觉分析、OCR、TTS、音乐和审核能力。能力注册表记录供应商、模型 ID、支持能力、同步/异步方式、参考图数量、比例、像素、时长、输入形式、地区、成本和限流。适配器提供 `submit`、`poll`、`verify_callback` 和 `fetch_outputs`。

不同供应商的结果存在差异，**禁止隐式跨供应商降级**；降级需由用户明确选择或在配方中配置。参考素材使用短期、单对象预签名 URL；跨境调用前按需缩小和移除 EXIF。若模型不能保持商品身份，默认考虑将真实商品抠图合成到生成背景上 [U]。

### 6.2 任务生命周期与转存

任务依次经历 `queued → submitting → running → ingesting → moderating → succeeded / blocked`，也可能失败、取消或退避重试。以 `(tenant, idempotency_key)` 保证幂等；供应商受理与外部 ID 落库之间崩溃时，通过客户端引用对账，不支持时记录时间并人工处理，接受极少量重复成本。多方案按资产分别记录，至少一个成功时可返回部分结果。

转存时限制像素、校验 MIME 和尺寸、解码重编码、清理或栅格化 SVG，用 `ffprobe` 限制视频编码、时长及尺寸。提交前审核提示词与参考图，转存后审核结果；按适用法规在转存和导出时添加隐式元数据及必要的显式标识。

### 6.3 地区化供应商候选

| 能力 | 中国优先 | 全球优先 | 判断依据 |
|---|---|---|---|
| Agent LLM | 豆包、通义、DeepSeek | OpenAI、Anthropic、Google | 按中文工具调用基准选择，统一接口。 |
| 图片生成/编辑 | 火山引擎 Seedream | GPT Image 或 BytePlus Seedream | 以商品保真测试为准。 |
| 拆层 | Seedream | BytePlus Seedream | 原文称最多 16 层 [V]，作为增强能力。 |
| 抠图 | 托管服务或自托管 BiRefNet 类模型 | 同左 | 原文指出 RMBG-2.0 权重为 CC BY-NC 4.0，商业使用需协议 [V]；分别核实各模型许可。 |
| 视频 | Seedance，确认 2.x API 权限 | BytePlus Seedance 或其他供应商 | 可用性存在二手资料冲突 [V2]。 |
| OCR | PaddleOCR 或云 OCR | 云 OCR 或视觉模型 | 用于文字核对。 |
| TTS/音乐 | 国内 TTS、授权音乐库 | 对应地区供应商 | 音乐授权需单独确认。 |

## 7. 可编辑文档设计

### 7.1 模型调整

图层顺序使用 `children` 数组顺序，未来引入 CRDT 时可用分数索引。文本支持 `spans[]` 样式、字体引用、自动适配、最大行数、对齐、行高、字间距和中文竖排。保留像素坐标并增加左右/居中/缩放约束，使比例变化时可确定性重排。图层增加语义角色、槽位、锁定和 Agent 可编辑标记；图片增加 fit、裁剪、遮罩、滤镜；资产引用固定版本 `asset_id@rev`；同时提供 group 与可裁切子元素的 frame；颜色和字体可引用品牌令牌。

现有原型的 `nodes[]` 与这些概念可以映射，应规划 v1 → v2 迁移。

### 7.2 操作 API

通过 `POST /v1/documents/{id}/ops` 和 `If-Match` 提交操作及来源，返回新修订号或 409 冲突。操作集保持封闭且精简，例如 `set`、`insert`、`remove`、`move_layer`、`reorder`、`replace_asset`、`resize_artboard`。在 `@designx/doc-core` 实现一次，浏览器乐观执行、服务端权威执行；Python 后端可用 Node sidecar 或共享测试数据的精简操作集。

不同图层/属性的操作可自动 rebase，真正修改同一属性才返回冲突；同一时间窗口用户修改优先。Agent 默认写入分支草稿，供用户预览并接受或撤销，也可由用户启用自动接受。

### 7.3 修订与撤销

使用操作日志（文档、修订、来源、操作、时间）及每 100 次操作或显式保存时的快照。客户端撤销使用逆操作；Agent 一轮作为一次可回退事务，如果用户后来修改了同一属性则提示冲突。命名版本作为用户检查点；导出记录 `(doc_id, rev)`。

### 7.4 渲染器选择

| 方案 | 特点 | 判断 |
|---|---|---|
| Konva | 图形变换能力好，文字编辑需覆盖 textarea，中文换行需自行处理 [V2]。 | 文字密集型场景较弱。 |
| Fabric.js | 具备 IText/Textbox 和隐藏 textarea 输入法 [V2]，可服务端渲染。 | 比 Konva 更适合文字，但仍依赖 Canvas 文本引擎。 |
| DOM/SVG + 变换手柄 | 浏览器原生文字布局和输入法，Chromium 可复用相同代码导出。 | MVP 推荐，需性能与一致性验证 [U]。 |
| Polotno / IMG.LY CE.SDK | 商业编辑器和渲染器，可加快开发。 | 团队不足两名编辑器工程师或验证失败时考虑购买，核实许可与锁定风险。 |
| tldraw | 无限白板，生产许可需确认 [V]。 | 可用于 Board 层，不适合作为设计画板核心。 |

建议用 50 个包含中文、混合文字、旋转、遮罩、150 图层及 4K 图片的文档，对比 DOM/SVG + Chromium 与 Fabric.js + node-canvas；目标 SSIM ≥ 0.99、150 图层编辑每帧 < 16ms，均为假设。若 DOM 性能不足，可换 Canvas/WebGL 舞台而保留文档模型。无限 Board 使用不同缩放层级的画板缩略图，仅激活画板挂载完整编辑器。

## 8. 视频生产架构

生成、编辑与渲染分别建模。MVP 使用有序镜头列表，每个镜头记录资产或生成任务、时长、字幕、转场，另有一条音乐轨和可选 TTS；多轨非线性编辑推迟到 M4。时间线示例的完整 JSON 见原文第 8.1 节。

MVP 以 FFmpeg 从时间线 JSON 构建 filtergraph；字幕由文档渲染器预先生成 PNG/ASS，再叠加到视频。浏览器用 `<video>`/`<img>` 顺序播放并显示 CSS 字幕，需要精确预览时生成低分辨率代理视频。Remotion 适用于后续模板化动态设计；CE.SDK 是商业购买方案；GStreamer/MLT 的学习成本较高。

FFmpeg 应运行在独立工作进程，限制 CPU、内存和执行时间（原文建议约为媒体时长 10 倍），每个任务清理临时磁盘。

## 9. 安全、合规与商业准备

1. **费用滥用：**工具层执行单轮、每日、套餐费用上限，使用幂等键，超过阈值时暂停审批。
2. **素材提示注入：**参考图、商品描述或抓取页面可能包含指令。工具采用最小权限和项目范围，将用户文本标记为数据，输出始终审核。
3. **跨租户访问：**每次工具调用和 API 请求在服务端检查 `project_id` 对应权限；预签名 URL 限定单个对象及短有效期。
4. **媒体解析攻击：**隔离解码、限制像素、重新编码，清理 SVG，限制 `ffprobe` 输入，及时更新 libvips/FFmpeg。
5. **凭据：**供应商密钥只保存在工作进程及适配器使用的密钥管理服务中；沙箱仅获得按调用范围授权的短期 MCP 令牌，网络出口采用白名单。
6. **中国上线：**原评审将生成式 AI 服务备案、算法登记、实名、内容安全、AI 标识、数据本地化和个人信息跨境要求列为上线前工作，适用性由法律顾问确认 [U]。
7. **全球上线：**原评审指出需评估欧盟 AI Act 第 50 条、GDPR、人像肖像权与 C2PA，适用范围和生效时间待确认 [U]。
8. **商业条款：**使用符合 API 条款的凭据，检查各模型输出所有权、赔偿、模型权重与字体嵌入许可。

使用 E2B 或其他沙箱时，按会话隔离、固定模板、限制出口、不持有供应商密钥；桥接仅向外连接，状态视为缓存而非权威数据。

## 10. 技术选型

| 层 | TypeScript 为主（推荐） | Python 为主（替代） |
|---|---|---|
| Web | React 19、TypeScript、Vite；原型从 JS 迁移。 | 相同。 |
| 文档核心 | `@designx/doc-core`，TypeBox/Zod → JSON Schema。 | JSON Schema → Pydantic 及 TS 类型；共享测试样例。 |
| 编辑舞台 | DOM/SVG + react-moveable，与 Fabric.js 做技术验证。 | 相同。 |
| API | Node 22 + Fastify/Hono，Kysely/Drizzle。 | Python 3.12 + FastAPI，SQLAlchemy 2/SQLModel。 |
| Agent | 自建兼容接口循环或 Agents SDK，统一 `AgentRuntime`。 | 相同思路，使用 Python 实现。 |
| MVP 任务 | Postgres + `SKIP LOCKED`，如 graphile-worker / pg-boss。 | 相同模式，如 Procrastinate，或 Hatchet。 |
| 增长工作流 | Temporal 或 Hatchet [V2]。 | 相同。 |
| 导出 | Playwright + Chromium，复用编辑器渲染代码。 | 即使后端为 Python，仍可用 Node 渲染 worker。 |
| 图片 | Python worker：pyvips、Pillow、onnxruntime。 | 相同。 |
| 视频 | FFmpeg，后期考虑 Remotion。 | 相同。 |
| 存储、事件和观测 | S3/OSS/TOS；SSE + Redis；OpenTelemetry、Sentry、Langfuse；imgproxy 或云图片处理。 | 相同，地区决定供应商。 |

无共享文档核心时，不应分别手写 Python 文档服务与 TypeScript 编辑器的操作逻辑。Go 仅在媒体代理、沙箱基础设施或网关出现已测量的吞吐瓶颈时考虑。

### M1：可编辑图片 MVP（8–10 周）

包含认证、项目、预签名素材上传、带操作日志的文档核心 v2、文字/图片/形状/分组/裁剪/约束编辑、10 个带槽位和角色的模板、品牌套件、三个配方（`product_hero_set`、`social_post`、`resize_set`）、含预览工具的 Agent、单供应商图片生成编辑与抠图、审核、标识、配额、PNG/JPEG/WebP 和原生格式导出、追踪及夜间基准评测。视频、协作、计费、真正无限 Board、市场、自托管模型及生产多 LLM 留待后续。

### M2：分镜视频（6–8 周）

分镜文档、异步视频适配器与续轮、TTS、音乐库、FFmpeg 和 Chromium 字幕卡、代理预览及任务对账。

### M3：电商产品化（8 周以上）

SKU 批量工作流、模板制作工具、资产搜索、基于约束的多尺寸重排、成本仪表盘、计费/积分、团队空间。

### M4：高级工作室

多轨时间线、实时协作、图层分解导入、局部重绘、可选代码沙箱；只有基准支持时才增加第二个 Agent 运行时。

### 12.2 指标和公平比较

逐项记录可编辑图层、OCR 文字、商品保真、约束满足情况，以及三名评审盲评的人类偏好、耗时 p50/p95、供应商与 LLM 成本、工具调用次数、未使用生成次数、用户修改到可接受状态的时间。

固定工具、供应商、模板、预算和输入，尽量使用相同底层 LLM，另做跨模型比较。比较仅配方、自建循环 + 配方、Agents SDK + 配方、Codex + MCP 以及规划/评估多 Agent；每任务每组至少运行三次，报告均值和离散程度。原文建议选择成功率距最佳方案不超过 5 个百分点、每份被接受结果成本不超过最佳方案 120% 的最简单方案；这些阈值需产品团队确认。评审盲测，并固定模型版本。
