# Part 1 · 执行层架构决策与范围（交付物 A）

## A.1 产品目标

| # | 目标 | 可度量的成功信号（提议） |
|---|---|---|
| G1 | 用户从**一句话、一个技能或一张商品图**出发，在同一个 AI 工作区里得到多个**可编辑**方案 | 生成结果 100% 以可编辑 Artboard 落到 Board，而不是只有扁平 PNG |
| G2 | **无限画布（Board）是主工作区**，用来组织想法、素材、方案、版本和参考 | 一个项目能在一个 Board 上放 ≥ 200 个 Artboard 加素材，交互流畅（目标见 Part 9） |
| G3 | 选中某个方案后，用对话**持续修改**，原稿保留，新版本可追溯 | 每次修改都生成新的版本节点，并带 lineage（来源）关系 |
| G4 | 能对文字、图片、形状、组合和布局做精细编辑；保存、重开、版本化，导出结果与编辑视图一致 | 导出与编辑视图像素一致性达到 SSIM ≥ 0.99（提议目标） |
| G5 | 平台对成本、失败、审核和合规**可控**：长任务可离开再回来，失败可解释可重试 | 所有任务最终进入终态；不存在“转圈但后台已丢”的状态 |
| G6 | 架构能演进到电商批量/SKU、视频、团队协作，不必推倒重来 | 每项扩展都有明确的触发条件和拆分路径（Part 6、Part 10） |

## A.2 非目标（MVP 及近期）

- **会员、点数、充值、支付交易**（资料 F065 明确排除）。只做**配额与成本记账**，不做计费。
- 通用 Agent 平台或插件市场（MCP/Skill marketplace）。
- 自研或自托管大模型训练平台、分布式 GPU 调度。MVP 全部通过外部模型 API。
- Photoshop 级像素编辑，或专业非线性剪辑（NLE）的同等能力。
- 宣称能把任意扁平生成图“无损”还原成原生可编辑文字和图层。图层分解只作增强。
- 实时多人协作编辑（在 Growth 阶段，见 Part 10）。
- 竞品分析、关键词分析、账号诊断等**依赖外部数据源**的分析类技能（资料 D09：数据来源未定）。

## A.5 MVP 边界

**以下是最终 MVP 目标，不是当前非 AI 阶段的完成清单。** 当前先完成账户/空间、项目、素材、手工模板、Board、Artboard 编辑、持久化、非生成任务与导出；涉及模型的生成、抠图、对话续改和 Harness/Sandbox 后接入，保留契约但不模拟为已完成能力。

**完整 MVP 上线能力（必须全部具备）**

1. 账户（手机号 OTP 或邮箱）、个人工作空间、项目列表。
2. **AI 无限画布工作区**：左侧对话，右侧 Board，与原型布局一致。Board 上可放 Artboard、素材、方案组和便签；支持平移缩放、选择/多选、拖动、吸附对齐、撤销重做、复制粘贴、快捷键和 LOD 缩略图。
3. 素材上传（预签名直传）、校验、缩略图、素材库、`@` 引用。
4. **3–5 个配方化技能（Recipe）**：商品套图、营销海报、图文封面、白底商品图、海报改尺寸。另有一个**通用 Agent 对话**，可调用这些配方和原子工具。
5. 生成多个**可编辑 Artboard 方案**，落到 Board 的方案组。
6. 对选中方案**对话续改**：默认生成新版本 Artboard 并保留原稿；对已有 Artboard 的就地修改以“修改提议”形式由用户确认。
7. **Artboard 精细编辑器**：文字（CJK、输入法、样式）、图片（裁剪、填充、替换）、形状、组合、图层、对齐、约束、品牌 token，并有撤销/重做和自动保存。
8. 保存、重开、命名版本、恢复：对话、Board、素材、进行中的任务都能恢复。
9. 导出 PNG / JPEG / WebP / 单页 PDF，由服务端用**同一渲染器**导出；另可导出原生 `.dxproj`。
10. 异步任务：进度、取消、重试、部分成功、超时、对账；SSE 实时推送。
11. 输入/输出内容审核、AI 生成内容标识（显式 + 隐式元数据）、配额、审计日志。
12. 可观测性：日志、指标、Trace、AI 调用记录，以及评测基准每夜运行。

**MVP 不包含**：批量/SKU、视频生成、多页文档、实时协作、分享链接、模板创作工具、图层分解导入、自托管模型、计费、移动端原生 App。

## A.6 主要架构决策

每项决策都给出备选方案和拒绝理由；状态和验证条件见 Part 10 决策日志。

| ID | 决策 | 理由 | 被拒/推迟的备选 |
|---|---|---|---|
| **AD-01** | **Creative Document 由产品拥有**：Board 文档与 Artboard 文档是版本化 JSON，schema 与操作（ops）定义在 `@dx/doc-core`。任何第三方画布库都只是“视图/交互层”。 | 数据可移植、导出一致、可迁移，不受 SDK 锁定 | 直接用 tldraw store 或 Fabric JSON 作为持久格式：会锁死数据格式，库升级和许可变化会直接冲击用户数据 |
| **AD-02** | **Board 与 Artboard 分层**：Board 负责空间组织；Artboard 编辑在专用编辑器中进行（同一页面内的聚焦模式） | 两类交互需求差异很大：Board 要的是数量与组织，Artboard 要的是排版精度与导出一致 | 在一个 tldraw 页面里把所有文字和图层都做成 tldraw shape：排版能力与导出一致性受限（Part 4 §D.2） |
| **AD-03** | **Board 引擎：tldraw 为首选候选，自研 DOM Board 为保底**。通过 `BoardEngine` 适配接口隔离，M0 做双路线 spike，按许可与验证结果做 go/no-go。 | tldraw 提供成熟的选择、吸附、历史、剪贴板和无障碍能力；但它是 source-available，商业生产需付费许可 | Excalidraw（MIT，手绘风格，自定义形状弱）；Konva/Leafer 自研 Board（工作量大）；React Flow（节点图导向，不适合设计画布）。见 Part 4 |
| **AD-04** | **Artboard 渲染器：React DOM/SVG，编辑器、Board 缩略图、服务端导出共用一套**；服务端导出用 Playwright 驱动 Chromium | 浏览器原生文字排版、CJK 断行、输入法与无障碍；导出与编辑一致性靠“同一份代码”保证 | Fabric.js 或 Konva 的 Canvas 文本引擎：要另做输入法和断行，服务端需 node-canvas 并保证字体一致；作为 M0 对照组 |
| **AD-05** | **TypeScript 单语言 MVP**：前端、API、Worker、渲染器都是 TS（Node.js LTS）。Python 只在后续自托管像素模型时引入，且**只处理像素，不修改文档**。 | 文档操作只有一份实现；招聘和工程链路更简单；原型已是 JS/React | Python FastAPI 控制面（会让 doc-core 出现双实现）；Go（MVP 没有性能瓶颈需要它） |
| **AD-06** | **模块化单体加独立 Worker 进程**：同一代码库产出 `api`、`worker`、`renderer` 三种进程 | 3–6 人团队的最低运维成本；事务一致性好 | 微服务拆分：拆分触发条件见 Part 5 |
| **AD-07** | **AI 三层执行模型**：直接操作（无 LLM）→ 配方 Recipe（确定性工作流内含 LLM 步骤）→ Agent 回合（工具调用循环）。另有评估器调用（视觉、OCR）作为质量门。 | 大多数技能本质是配方；Agent 只处理模糊需求；可测、可控成本 | 所有请求都过 Agent：昂贵、不稳定；多 Agent 框架：推迟，以基准测试结果为准 |
| **AD-08** | **E2B Sandbox 内 Harness + Codex SDK**（用户已确认，见 ADR-0001）。Worker 调度沙箱和回合，Harness 调用 Codex SDK；业务工具经控制面校验，成果经过摄取后入库。 | 遵循用户明确指定的最终执行架构；复用 Codex 执行能力，隔离运行环境；业务真相源和权限不下放 | 原自研轻量 Agent loop 被替代；不自动切换为其他 Agent SDK 或其他宿主；真实集成后续验证 |
| **AD-09** | **PostgreSQL 为业务状态真相源**：业务数据、文档 op-log、快照、任务队列（pg-boss）、事件 outbox、SSE 广播（LISTEN/NOTIFY）都在其中。二进制及经批准的运行检查点在对象存储；沙箱/SDK 状态不是业务真相源。MVP **不引入 Redis**。 | 少一个业务有状态组件；文档、任务与事件一致提交，投递方式经验证确定 | Redis/Valkey 加 BullMQ：触发条件见 Part 6；Temporal 和 Hatchet：触发条件见 Part 6 |
| **AD-10** | **AI 默认非破坏性**：生成和续改默认产出新 Artboard 版本；对已有 Artboard 的修改以 Proposal（修改提议）提交，用户确认后才应用 | 消除大部分 AI 与用户的并发冲突；与原型“保留原稿”体验一致；建立信任 | AI 直接改正在编辑的文档：冲突与信任问题 |
| **AD-11** | **供应商适配器做成进程内库，并配能力注册表**；不做隐式跨供应商回退 | MVP 每种能力 1–2 个供应商即可；回退会改变创作结果 | 独立网关服务加路由策略：拆分触发条件见 Part 6 |
| **AD-12** | **合规内建**：输入/输出审核、AI 生成内容显式与隐式标识、模型来源公示、配额、审计都在 MVP | 国内上线的前置条件 [假设：法务确认] | 上线后补：属于阻断性风险 |
| **AD-13** | 原型**渐进演进**：保留 UI、信息架构、交互和视觉；替换数据层与生成层；把 `design.nodes` 迁移到 Artboard v1 | 原型是已验证的交互资产 | 推倒重写 |

## A.8 对 `architecture-review.md` 的批判性评估

该评审是本会话早前的独立意见。复核后的采纳情况如下：

| 评审观点 | 结论 | 说明 |
|---|---|---|
| 不用“E2B 中的 Codex”作为默认 Agent 宿主，改用控制面内的工具循环加配方 | **被用户新决策替代** | 2026-10-31 确定 E2B 内 Harness + Codex SDK。保留确定性配方与 Worker 调度；不能继续把旧评审的拒绝理由当作当前决策。区域可用性等作为待验证条件，不断言不可用。 |
| 先确定首发区域 | **采纳** | 本方案给出临时的 China-first 设计，并列出 Global 差异 |
| DOM/SVG 加 Chromium 导出，保证一致性 | **采纳，并补充** | 评审没有讨论 Board 层大量 Artboard 的渲染成本。本方案补充 LOD：缩小时用位图缩略图，放大到阈值才挂载 DOM 渲染（Part 4）。 |
| “无限画布仅做缩略图视口，MVP 保留原型 Board” | **修正** | 本次需求把 Board 定为一等能力，MVP 必须交付完整 Board 交互。评审低估了这部分工作量。 |
| MVP 引入 Redis 做 pub/sub 和限流 | **修正** | MVP 用 Postgres LISTEN/NOTIFY 加表级令牌桶即可，少一个组件；Redis 有明确的引入触发条件。 |
| 推荐 TS 栈或 Python 栈二选一 | **收敛** | 明确选 TS 单语言 MVP；Python 只做像素处理 Worker，且不修改文档。 |
| Agent 修改默认为“草稿分支” | **简化** | 改为“新版本 Artboard（默认）加 Proposal（就地修改）”两种机制，概念更少，也与原型一致。 |
| 没有注意到资料中“个人作品、非商业”的定位 | **评审遗漏** | 这会影响 tldraw、Remotion 许可和合规范围，本方案列为 Q1。 |
| 24 项基准测试 | **沿用并扩展** | 增加 Board 性能、CJK 排版、并发与恢复类用例（Part 9）。 |
| “编辑器 SDK 可外购（Polotno / CE.SDK）” | **保留为备选** | 两者都是商业 SDK；若编辑器工程能力少于 2 人可重新评估（决策日志 D-11）。 |
